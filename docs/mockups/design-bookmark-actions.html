Bookmark item — notes, actions, archive

Design exploration for the shared bookmark row (LinkRow, used by the dashboard and collection detail). Goal: notes preview + expand, per-row actions (archive, add-to-collection, remove-from-collection), and inline editing of notes + tags. No implementation yet — this mockup is the design proposal. Rows below mirror the current LinkRow markup (ul.link-list > li > article > header/footer) with the app's verbatim tokens; every new element is contextual, so a bookmark with no note and no extras looks exactly like today.

Variant A decisions.
  • Tone: muted --text-2, 0.82rem, left border accent + no ✎ icon — reads as a quiet annotation, still legible; the border separates it from tags above without a background chip.
  • Clamp: -webkit-line-clamp: 1 — collapse is pure CSS; the More link shows only when a note exists and overflows (render the toggle only if the note is longer than the preview, decided server-side or by htmx swap).
  • Expand: details.note-toggle + .note:has(.note-toggle[open]) — native, no JS, matches "native CSS first" in docs/css-guidelines.md. Label flips More/Less via the same :has().
  • No duplication of the note text in the DOM (preview and full are the same element).

3. Inline edit — notes + tags (title/domain read-only)

One panel, one save. Tags reuse the add-form semantics (comma-separated). Title and domain are displayed, not editable — they are the bookmark's identity.

Why one panel for notes and tags.
  • Notes (FR-22) and tags (FR-3) have the same lifecycle — "I'm touching this bookmark" — so one Edit notes & tags menu item beats two nearly identical panels.
  • Editing is a temporary state, not a page: the row swaps to the panel and back (htmx), no navigation.
  • Title/domain stay read-only — changing them would mutate the bookmark's identity; the add-form already covers re-saving a different link.

Why confirm, why this wording.
  • Archive is reversible, but it removes the row from the list — the confirm (native hx-confirm in the app, confirm() here for the demo) prevents fat-finger loss.
  • Wording states the consequence and the escape hatch: "Archive this bookmark? You can restore it later."
  • Matches FR-1: soft-delete — archived_at set, hidden from recent/search/filtered; restore + archived filter come later.

5. Edit collections — search + multi-select popover

Same 3-item menu on every page; the popover is the single skill for membership — add and remove, one go. Recommended input: a small popover with a search field and a checkbox list (multi-select), because it scales to many collections, is keyboard-driven, and degrades to a plain checkbox form without JS.

Why search + checkboxes (and the alternatives I considered).
  • Search + checkboxes (chosen): exact match on the thing users know (names); checkbox = explicit add/remove; Save = one htmx round-trip. No-JS fallback: the same form posts on submit.
  • Native <select multiple>: smallest code, but ugly on desktop, no search, easy to mis-click; rejected.
  • Instant-toggle chips (click chip = add/remove immediately): fewest clicks, but one request per chip, no "cancel", no search, and accidental toggles are easy. Good later as a progressive enhancement shortcut; not the primary.
  • Only collections the user owns are offered (CL-5: shared-collection bookmarks keep the original author).
How it works (mechanics).
  • Open/close: the ⋯ is a <details> — native toggle, no JS. The popover itself uses the popover API (popover="auto"): light-dismiss works out of the box — click outside or press Esc and it closes. Selecting “Edit collections…” closes the ⋯ menu and opens the popover in its place; Save/Cancel close it again.
  • Content: the popover is server-rendered with all of the user's own collections, preloaded, current membership shown as checked boxes (so from the collection page, that collection arrives checked — unchecking it is the “remove from this collection” action). No extra fetch on open; htmx refreshes the popover if membership changed elsewhere.
  • Volume & scroll: no artificial cap — the checkbox list has a max-height (~8 rows) with its own scrollbar; search filters it down, so a 50-collection library stays navigable. The 4-collection demo here just truncates for space.
  • Accessibility: real form controls — checkboxes are keyboard operable, the search input filters, Save/Cancel are buttons; the popover API wires focus + Esc automatically.

  • What happens on the collection page: after archiving, the row leaves that list too — the bookmark stays linked to the collection (FR-1: archives stay visible in collections via the filter) but stops appearing in the default browse view. If you'd rather it stay, say so when we implement.
