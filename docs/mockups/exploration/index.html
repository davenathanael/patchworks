Patchworks — design exploration

Four divergent directions for the home screen, quick-add, collections, reading queue, feed reader, and search. Nothing from the current build is held constant on purpose — each candidate makes its own argument about information architecture, interaction model, and visual personality, so they can be compared fairly.

Mockups are self-contained HTML. Open a candidate directly in a browser. Each file shows wide (desktop) and phone (390px) frames.

The candidates

Candidate A

Workbench

dense · utilitarian · keyboard-first · two-pane

The utility extreme. No sidebar, a persistent command bar with a visible query-syntax search, and a list with an inspector pane. Every row action is permanently visible instead of hidden behind a kebab. Monospace metadata, hairline rules, no card chrome.

  • Answers: "if this were a tool I use 50× a day, what would it be?"
  • Strongest at: retrieve, bulk triage, power search.
  • Weakest at: calm reading, showing off notes.
 Candidate B

Inbox

airy · calm · card-based · mobile-native composer

The calm extreme. One centered column, no persistent navigation chrome, generous cards with real presence. Quick-add is a bottom floating composer, the pattern your thumb already knows from every phone. Largetype, soft corners, quiet palette.

  • Answers: "if this were a place to browse rather than operate, what would it be?"
  • Strongest at: read-heavy triage, notes, mobile.
  • Weakest at: scanning 200 results, dense metadata.
 Candidate C

Ledger

typographic · calm-dense · table-first · serif body

The reconciliation of "airy and calm" with "dense and utilitarian." A narrow column, rows aligned into real columns like a printed ledger, body text in a serif at generous measure, chrome stripped to a thin rail of labels. Dense in information, calm in texture.

  • Answers: "can information density feel calm? what would that look like?"
  • Strongest at: organize-heavy work, seeing everything at once.
  • Weakest at: mobile, anything needing more than three columns.
 Candidate D

Split Deck

interaction-first · three-pane · unified stream · palette

The interaction-model divergence. Folders, list, reader — three panes, all visible at once. Bookmarks and feed items become the same kind of object in one mixed stream, so triage is one action vocabulary. Command palette overlay for everything. On mobile it collapses list → reader.

  • Answers: "what if feeds and bookmarks are one inbox?"
  • Strongest at: RSS/reader integration, keyboard flow, never losing your place.
  • Weakest at: mobile-first, simple add-and-forget.

Constraints fed into all four

Primary useretrieve-heavy, read-heavy, organize-heavy — so no single-screen-only assumption; list, search, and collections all matter
Roadmap weightvisible query-syntax search, share links + a real mobile pass, and an RSS aggregator with per-feed triage + auto-tagging
Densitydeliberately split — candidates were allowed to disagree rather than all landing in the middle
Fixednothing. Palette, type, corners, sidebar, and interaction model are all up for replacement

Shared constraints that apply regardless of direction: the list is the interface (no bookmark detail page); collections carry owner/editor/viewer roles and need share links; archived is a distinct recoverable state; quick-add must survive with JS disabled; feeds add a subscription-management surface and per-item read state separate from bookmark read state.
